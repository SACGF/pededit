# backend/ — agent notes

Django 5 + Django REST Framework + simplejwt. Project package is `peded/`,
the single app is `api/`.

## Running

```
cd backend
.venv/bin/python manage.py migrate
.venv/bin/python manage.py runserver 8000
.venv/bin/python manage.py test api
```

Use `uv` for environment work (`uv venv`, `uv pip install -r requirements.txt`),
never pip directly. Config is read from `/etc/pededit/pededit.json` by
`site_config.py` (database_url, cors_allowed_origins, allowed_hosts, debug,
google_client_id, github_client_id, github_client_secret, and the production
keys https, hsts_seconds, hsts_include_subdomains, throttle_rates,
num_proxies). The file must exist
or Django will not start. A SQLite `database_url` is fine for local dev. The
secret key is generated into `backend/secret_key.txt` on first run if not
supplied.

## Production settings and rate limits (#47)

- `"https": true` in the site config is the one switch for the HTTPS
  redirect, secure cookies and HSTS (`peded/security.py`, a function of the
  config values so tests can call it both ways). Off, it sets nothing and
  development is untouched. `deploy.sh` runs `check --deploy --fail-level
  WARNING`; a warning accepted on purpose is silenced by name in that file
  with the reason (`security.W021`: no HSTS preload).
- `api/health/` is in `SECURE_REDIRECT_EXEMPT`. `deploy.sh` asks Gunicorn for
  it over plain HTTP on loopback, and a redirect there fails every deploy.
- Rate limits are DRF throttles in `api/throttling.py`, set per view, never
  as a DRF default: sign-in, token refresh and anonymous create only. GET,
  PATCH and DELETE of a pedigree are deliberately unlimited (auto-save).
  Rates are `settings.THROTTLE_RATES` (site config `throttle_rates`), not
  DRF's `DEFAULT_THROTTLE_RATES`, which is copied at import and ignores
  `override_settings`.
- A caller on the box with no proxy headers (`is_local_request`, shared with
  the health check) is never limited. That is what keeps the tests, local
  development, CI, the page checks and the flows clear of the limits: Vite's
  proxy adds no `X-Forwarded-*`. A throttle test must send
  `HTTP_X_FORWARDED_FOR` or it tests nothing.
- Counters are in the `throttle` cache, a `DatabaseCache` table
  (`createcachetable`), so the Gunicorn workers share them; the default
  local-memory cache counts per worker. The test runner creates the table
  itself. If the table is missing the request is allowed and the error
  logged. A new limited endpoint (the render endpoint, #38) takes a
  `ClientAddressThrottle` subclass with its own scope and a default rate in
  `site_config.DEFAULT_THROTTLE_RATES`.

## Data model (`api/models.py`)

- `Pedigree` — UUID primary key, nullable `owner`, `title`, `data` JSONField
  that mirrors `layout-engine/src/types.ts` exactly. `PedigreeDataSerializer`
  only validates the known fields; `PedigreeDataField` then stores the
  submitted JSON untouched, so unknown fields survive and absent optional
  fields stay absent (the JSON format promises this). Never switch back to
  storing `validated_data`: DRF drops undeclared keys and fills defaults,
  which lost `lifeStatus` on every save. Still add new `types.ts` fields to
  the serializer so they get validated.
- `TagPreset` — a signed-in user's saved condition or tag ("My library"
  in the Conditions and tags dialog). Pedigrees always
  carry their own copy of tags, so presets are a convenience only.

`PedigreeDataSetTests` in `api/tests.py` posts every file of the shared test
data set (`test-data/pedigrees/`, #167, generated by the frontend's
`fixtures/dataset.ts`) and checks what `manifest.json` says the server does:
valid files stored unchanged, files with a missing or mistyped field refused.
The serializers check each field's shape only, so a pedigree whose structure
is wrong (an id that does not exist, a cycle) is stored today; the manifest
marks those `accepted-unchecked` and #170 is the decision to refuse them.

## Access rules (`api/views.py`)

- `owner=None` pedigrees are **anonymous**. Anyone who knows the UUID can
  read, update or delete them. This is deliberate: it is how the no-account
  mode works. The UUID is the capability.
- `GET /api/pedigrees/` (list) requires auth and returns only owned ones.
- Create without a token makes an anonymous pedigree; with a token it is
  owned.
- `/api/tag-presets/` is auth only and scoped to the owner.
- An owned pedigree answers 404 to everyone but its owner, so its link is
  not a way to share it. An anonymous pedigree stays anonymous when a
  signed-in user opens or edits it: nothing ever sets `owner` after create.
- These rules are pinned by `PedigreeAccessTests` and stated to users on the
  landing page (#178, `YourData` in `frontend/src/pages/LandingPage.tsx`).
  Change that text with any change to them.
- There is no `api/admin.py`, so Django admin shows users only, not
  pedigrees. `Pedigree.data` is plain JSON in the database, readable by
  whoever can read the database. Delete is a hard delete, and there is no
  way to delete an account from the app.

## Auth

- JWT access tokens live 15 minutes, refresh tokens 7 days and rotate.
- `api/social_auth.py` — Google (ID token verified server-side) and GitHub
  (code exchange) both find-or-create a Django user by email and return a
  token pair.
- There is no username and password sign-in and no registration (#51,
  removed: direct OAuth works, so the planned move to Clerk was dropped).
  Tokens are issued only by the two social views and by the `agent_token`
  management command for the page checks; `auth/token/refresh/` renews
  them. Django admin still uses a password (`createsuperuser`), which gives
  no API token. A server with no Google or GitHub client ID has no
  accounts, only anonymous pedigrees, and the login page says so.

## URLs

`peded/urls.py` mounts admin, simplejwt's token refresh view, and `api/urls.py`
(health, pedigrees, tag-presets, auth/me, auth/google, auth/github).

`GET /api/health/` (`api/health.py`, #50) has `authentication_classes = []`
on purpose: with the default JWT authentication a stale token in the request
would turn a healthy app into a 401. It is the URL uptime monitoring polls,
so anything added to it must be cheap and must mean "users are affected" when
it fails.

- It fails on low disk space (`HEALTH_DISK_PATHS`, `HEALTH_DISK_MIN_FREE_MB`,
  from the site config) because `SELECT 1` keeps passing on a full disk while
  every save fails.
- The version is the git commit (`peded/version.py`, cached at import,
  `PEDEDIT_VERSION` overrides). It is returned only when `REMOTE_ADDR` is
  loopback and the request carries no proxy headers, which is `deploy.sh`
  asking Gunicorn directly. Do not put it back in the public answer: the repo
  is public, so a commit tells a scanner which fixes a server is missing. The
  Django test client counts as local; pass `HTTP_X_FORWARDED_PROTO` to test
  the public answer.
- It has its own `head()`. Monitors send `HEAD`, and without it Django runs
  `get()` and Gunicorn logs a warning about the dropped body on every poll.
- Errors and free-space figures are logged, never returned.
  `settings.LOGGING` filters the check out of runserver's request log;
  production does the same in `deploy/gunicorn.conf.py` and the Nginx vhost.

`manage.py usage_stats [--days N] [--json]` (#78) prints signed-in users and
signed-in vs anonymous pedigrees created and edited in the window; `deploy.sh`
runs it at the end. Social login never sets `User.last_login`, so "active
users" means owners of a pedigree touched in the window, and anonymous users
can only be counted as pedigrees. `claude_agent` is excluded.

Static files are served under `djstatic/` so they do not collide with the
Vite build.
